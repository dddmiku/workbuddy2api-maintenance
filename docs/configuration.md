# 配置说明

配置从 `config.json` 加载。完整模板见 [config.example.json](../config.example.json)，默认值和校验逻辑见 `cmd/server/config.go`。

## 常用配置

| 字段 | 默认值 | 说明 |
|---|---|---|
| `listen` | `:7863` | 容器内监听地址；宿主机映射由 Compose 控制 |
| `api_key` | 空 | 单密钥模式的调用密钥；多密钥模式首次建库时用于迁移 |
| `api_keys_file` | `./data/api_keys.json` | 持久化密钥库路径；留空即用默认值 |
| `api_keys_enabled` | `true` | 密钥管理总开关；显式写 `false` 才关闭，回到单密钥 / 免鉴权模式 |
| `api_keys_socket` | 密钥库同目录下 `api_keys.sock` | 多密钥管理通道 |
| `usage_file` | 密钥库同目录下 `usage.json`（无密钥库时为不启用） | 按 API key 累计的 token 用量账本 |
| `auth_dir` | `./auths` | 启动时加载 `workbuddy*.json` |
| `state_file` | `./data/state.json` | 账号池状态文件 |
| `server.max_body_mb` | `8` | 入站请求体上限，必须大于 0 |
| `server.outbound_image_budget_mb` | `7` | 出站图片字节预算；非正数关闭裁剪 |
| `prompt.mode` | `passthrough` | 保留客户端指令；`custom` 才执行显式替换 |
| `prompt.file` | 空 | `custom` 模式使用的提示词文件 |
| `prompt.act_note` | 内置运行约定 | 追加到「带工具的请求」第一条 system 末尾，Chat Completions 与 Responses 两条路径都生效；强调待执行动作必须同次返回工具调用；`off` 关闭，也可写自定义文本 |
| `update.enabled` | `true` | 是否允许管理台一键热更新 |
| `update.repo` | `dddmiku/workbuddy2api` | 拉取更新的 GitHub 仓库（`owner/name`） |
| `update.token` | 空 | 私有仓库读取用 token；公开仓库留空 |
| `update.dir` | 数据目录下 `updates/` | 下载件与 `current` 指针的存放目录 |
| `pool.max_in_flight` | `3` | 单账号并发上限；0 表示不限制 |
| `session_sticky.enabled` | `true` | 按客户端会话键选择账号 |
| `global.enabled` | `true` | 是否允许国际版账号路由 |
| `features.reasoning_loop_guard` | `true` | 重复推理保护的全局默认值；每把密钥可单独开启或关闭 |
| `features.reasoning_loop_stop_only` | `false` | 命中循环只停止该次请求，不做同账号重发（启动初值；管理台「系统」页可热切换） |

配置模板中的示例值不等于安全的部署默认值。对外部署前必须设置调用密钥。

## 旧输入倍率配置

`server.input_token_scale` 与环境变量 `WB2A_INPUT_TOKEN_SCALE` 已弃用，不再用于调整输入、缓存或合计用量。Responses、Chat、请求日志与账本都使用上游已观测的原始用量；移除旧倍率配置不会重算历史账本。

为兼容现有部署，历史允许的 `[1,5]` 范围内有限数值仍可读取。显式配置旧字段或环境变量时，即使值为 `1`，启动也只告警一次并忽略；完全未配置时不产生这条告警。旧有效值不会改变响应，也不会阻止升级启动，`null` 等非法值仍按配置校验报错。建议从 `config.json`、Compose 或服务环境中删除遗留字段和环境变量，完整示例已不再包含它们。

提前压缩由客户端配置控制。Codex 使用 `model_context_window` 与 `model_auto_compact_token_limit`；`/v1/models` 的 `context_length` 是模型目录元数据，不会自动下发客户端窗口或压缩阈值。配置位置与验证方式见 [Codex 长会话](codex.md#长会话的上限口径)。

## 账号调度与会话隔离

普通选号按模型和区域过滤可用账号，再按实测成本、余额、闲置与成功率分配。当已确认免费和未测试账号同时存在时，每四次普通分配给未测试账号一次轮询机会，其余保留免费优先；已确认收费账号不会因此进入免费层。探索仍遵守禁用、模型限额、余额耗尽、在途上限及本次已尝试账号的排除规则。不同模型和区域各自计数，粘性请求不消耗探索次数。

启用会话粘性后，同一会话优先沿用可用的绑定账号；新会话优先分配尚未绑定的可用账号，全池已有绑定时按会话键散列分配。这是保留上下文缓存的调度，不保证每一条请求严格轮流换号。失败后会回落普通选号，最终成功账号写回绑定。

多密钥模式用已鉴权的密钥 ID 隔离会话键和上游关联头。不同调用密钥即使提交相同 `conversation_id`、`prompt_cache_key`、`metadata.user_id` 或显式关联头，也不会共用绑定或互相解绑。同一密钥内优先读取 `metadata` 会话 ID、顶层会话 ID、`client_metadata` 线程/会话 ID，最后回落缓存键及用户 ID；Chat 与 Responses 的识别一致。原始消息正文不改写。升级后旧的未隔离绑定不再用于多密钥请求，新绑定会重新建立；单密钥模式保留原有键。

一个会话标识都不发的客户端（例如 narrafork 的 `/v1/chat/completions`，请求体顶层只有 `model`、`messages`、`stream`、`tools` 等，既无 `conversation_id` 也无 `metadata`、`prompt_cache_key`）此前粘性完全不生效，同一对话每轮换号、上游提示缓存整段失效。这类请求现在会从正文派生对话级回退键：取**第一条** user 消息的文本做哈希，因此同一对话的后续轮次（首条 user 不变、末尾不断追加）保持同一账号，不同对话各自绑定。回退键只用于账号绑定，不参与上游关联头的聚合粒度（那部分仍按对话轮）。客户端裁剪历史把首条 user 消息删掉时键会变化、绑定重新分配，只影响缓存亲和；两条对话恰好以同样文本开头时会共用绑定，粒度仍细于 `metadata.user_id` 回退。

## 重复推理保护

`features.reasoning_loop_guard` 默认开启。当模型长时间反复输出少量短行时，网关可停止该次请求。保护同时覆盖两条文本流，错误码不同：

| 被监控的文本 | 错误码 | 窗口 | 附加要求 |
|---|---|---|---|
| `reasoning_content`（推理） | `upstream_reasoning_loop` | 32 条短行 | 窗口内最多 16 种不同短行 |
| `content`（正文） | `upstream_output_loop` | 64 条短行 | 最多 12 种不同短行，且出现最多的行占 75% 以上 |

正文侧单独设码，是因为它已经可能被用户看到：调用方据此区分「模型在思考里打转」和「重复正文正在刷屏」。两条流都要求窗口内重复行覆盖至少 95%，只有不超过 32 个字符的短行可以计为重复。

判定完全依据**重复形态**，不设任何字符量下限。此前按「自上次进展以来累计推理达到 N 个字符」触发，N 无论取多少都是拍出来的数：取高了漏检真实循环，取低了压缩模型能力，而且每次调整都会再造一次「参数挡住检测」的问题。现在只问一件事——最近这一小段输出是不是在反复说同样的话。

这是减少继续空转的启发式保护，不是对上游循环原因的诊断。

管理台「密钥管理」的每一行都有「重复推理保护」开关，创建和编辑密钥时也可设置。明确设置的密钥按自身开关执行；旧密钥或未设置该字段的密钥沿用全局默认值。修改立即作用于后续请求，不需要重启，也不会改变密钥的启停、模型白名单或其他用户的设置。已开始的请求继续使用开始时的策略。

检测仅匹配 `deepseek-v4.1-flash` 及其 `cn:`、`global:`、`sg:` 前缀形式（`sg:` 只用于匹配该别名，模型路由仍只认 `cn:`/`global:`，未知前缀会按裸名原样发给上游）。匹配时忽略模型名首尾空白和大小写，不改变已有的模型路由规则。每个 choice 分别检测，以下条件必须同时满足：

- 已收集最近 32 条（正文侧 64 条）可重复的短行，即去除首尾空白后不超过 32 个 Unicode 字符的行。
- 窗口内不同短行不超过 16 种（正文侧 12 种），重复行覆盖至少 95%。

两类行不进入窗口：超过 32 个字符的长行（含超过 4096 字符检测缓冲上限的行），以及 ``` 围栏标记与围栏内部的行。长行永远不可能与任何东西重复，让它们占窗口格位只会稀释覆盖率——实测两份真实循环里长行分别占 19.2% 与 42.9% 的非空行，旧语义下覆盖率天花板被压到约 81% 与 57%，95% 这条线要等整段输出快结束才勉强达标，这正是「模型明显在抽风、保护却没反应」的根因。围栏内的代码片段则天然带重复结构（`}`、`...`、`status = {`），排除后本地近五千段真实推理零误报。

推理窗口由任何可见进展重置：含非空白新增文本的正文或 refusal、新工具 ID 或名称、非空工具参数增量都会重新计数。正文窗口只由非正文进展重置（refusal、新工具 ID 或名称、非空工具参数增量）——正文本身正是被监控的载荷，不能自我重置，否则重复正文每加一行就会把自己的窗口清空。重复已有的工具 ID/名称、role、usage、type/index、空白正文或空元数据不算实际进展。

命中后网关默认先在**同一个账号**上重发一次，而不是直接把失败交给调用方。循环是上游模型行为、与账号无关，换号会丢掉刚建立的上下文缓存；同账号重发通常能拿到干净的一轮。重发只在客户端还没有收到任何字节时进行：

- 非流式 Chat 与 Responses 本来就是读完才回，重发对调用方完全无感。
- 流式请求在「只有推理、还没有正文/拒绝/工具进展」的阶段把帧压在内存里。这段压制期命中循环时客户端仍是零字节，可以整段丢弃并重发。
- 正文阶段同样保留这个能力：只要正文还不能排除短行循环（没有出现超过 32 字符的长行、没有出现空行、不同短行不超过 2 种），就先压住不发。命中时客户端仍是零字节，可以整段重发；一旦出现任一反证就立即放行并转为实时透传，此后命中只能照旧回报错误。正常回答的第一行通常就超过 32 字符，因此实际只多等一个行尾。
- refusal 与工具进展一出现就放行，它们不是被监控的载荷。
- 压制有上限，长输出不会无限等待：推理累计到 65536 字符、正文累计到 32768 字符、缓冲达到 16 MiB、推理压制满 60 秒、或正文压制满 8 秒时立即放行并转为实时透传。窗口缩到 32 行之后，真实循环通常在几千字符内就命中（实测两段线上循环分别在整段的 63% 与 64% 处触发，此前是 99%），这些上限只用于兜住「一直不像循环、但也不产生长行」的异常输出。正文侧时限单独设短，是因为没有换行的短回答不该被压到 60 秒。
- 字节上限必须高于字符上限的实际开销，否则会先于字符上限生效。上游把推理切成约 220 字节的小帧、每帧只带一两个字符（实测 124–222 字节/字符），旧版 2 MiB 折合仅约一万字符，缓冲会在判定之前放行，客户端先看到重复文本再收到 422。16 MiB 覆盖 65536 字符在最高字节率下的开销（约 14 MB）。峰值并发实测约 7 条在途请求，按每条最多 16 MiB 计约 112 MB。

重发一次后仍然命中，或客户端已经收到内容时，非流式 Chat 与 Responses 返回 HTTP 422；已开始的流式请求保持 HTTP 200，Chat 发送错误事件，Responses 发送 `response.failed`，不发送成功终态。错误码按触发的文本流给出（推理侧 `upstream_reasoning_loop`、正文侧 `upstream_output_loop`）。重发没能建立（上游连接失败或直接报错）时返回 502 并把原因写回客户端，不会静默结束。网关关闭本次上游流、不换号、不处罚账号，也不解除原有会话粘性。

`features.reasoning_loop_stop_only` 默认 `false`。设为 `true` 时保留「命中即停止」的单项停止语义：命中循环只关闭该次上游流并如实回报错误，不再同账号重发。适合不希望网关替调用方重试的场景；代价是用户会看到这次失败，需要自己重试。它是服务级开关，对全部请求生效，与每把密钥各自的 `reasoning_loop_guard` 开关相互独立——密钥开关决定「检不检测」，这个开关决定「命中之后重发还是只停」。

管理台「系统」页可以直接切换这个开关，改完立即作用于后续请求，**不需要改配置文件、也不需要重启网关**；配置里的值只作为进程启动时的初值。已经开始的那次请求沿用开始时的语义，不会被中途改判。运行期切换只走本机管理通道（`GET`/`POST /features/reasoning-loop`），普通调用密钥改不了所有调用方看到的行为。

```json
{
  "features": {
    "reasoning_loop_stop_only": true
  }
}
```

无论最终成功还是失败，被丢弃的那一轮上游确实已经生成并计费，用量照实累计、不额外计请求数。触发的请求同时计入「失败请求」与「用量未完整返回」。已经观测到的输入、输出、缓存和扣费原值仍会保留；即使较早帧曾同时返回输入和输出用量，后续继续生成后再触发保护，剩余用量仍是未知，不按文本长度推算或补齐。

超过 32 字符的矩阵、SQL 等长行不作为重复候选，响应原文不会因内部检测缓冲而截断。正文侧还有「出现最多的行占多数」与空行放行两道防线，但合法的重复短行仍可能误报，无换行的循环也不在这一规则的覆盖范围。业务本来就需要大量重复短行时，可关闭对应密钥的开关。也可以为未单独设置的密钥修改全局默认值：

```json
{
  "features": {
    "reasoning_loop_guard": false
  }
}
```

修改全局配置后重启服务使默认值生效（或在管理台「系统」页直接热切换）；已单独设置的密钥仍按自身开关执行。关闭保护的请求不再按这条规则中止重复推理，原有超时及协议完整性检查继续生效。

## 单密钥与多密钥

持久化密钥库默认启用，路径 `./data/api_keys.json`。`api_keys_file` 留空（包括没写这一项、写成空串、写成 `null`）都按这个默认值走，管理台可以直接建密钥，不需要先改配置。**启动时库里一把密钥都没有是正常状态**：库文件会自动创建，用户随后在管理台创建第一把即可。

要关闭密钥管理只有一种写法：显式 `"api_keys_enabled": false`。此时回到单密钥模式（`api_key` 非空）或免鉴权模式（`api_key` 也为空）。之所以不用「把 `api_keys_file` 写成空串」当关闭信号，是因为历史 `config.example.json` 里这一项就是空串，照抄它的部署很多——把空串解释成关闭，这些用户就会继续看到「密钥管理尚未启用」而建不了密钥。

启用密钥库后由它负责鉴权：

1. 文件不存在时创建密钥库；非空 `api_key` 迁移为现有密钥。
2. 文件已存在时加载原有内容，不再次导入或覆盖。
3. 空库拒绝调用，不能通过清空 `api_key` 恢复免鉴权。
4. 配置文件损坏、密钥库不可读或 socket 不可用会阻止正常启动，应根据日志修复。

管理台读的是原始 `config.json`，网关读的是归一化后的配置，两边对「没写这一项」的判定必须一致（`panel/key_management.py` 的 `DEFAULT_API_KEYS_FILE` 对应 `cmd/server/config.go` 的 `DefaultAPIKeysFile`）。分叉的表现就是网关已经能用密钥、面板却报「密钥管理尚未启用」。

推荐布局：

```json
{
  "api_keys_file": "./data/api_keys.json",
  "api_keys_socket": "./data/api_keys.sock"
}
```

不需要密钥库的部署：

```json
{
  "api_keys_enabled": false,
  "api_key": "自己的调用密钥"
}
```

摘要继续用于鉴权。2.1.1 起新建密钥另外保存 AES-256-GCM 加密副本，管理员可以在列表中再次复制；完整密钥不放进列表、日志或浏览器本地存储。旧记录不会重置或换发：后续以原密钥成功鉴权时，网关会补齐加密副本，之后即可复制；尚未使用过的旧记录无法仅凭摘要还原。

加密文件路径是密钥库路径加 `.enc-key`，上例为 `./data/api_keys.json.enc-key`，权限为 `0600`。备份时一起保留密钥库和这个文件，以及原有网关配置、账号目录和状态。已有加密副本但加密文件缺失时不会擅自换新文件；已有摘要鉴权继续工作，复制和新建需先恢复加密文件。复制只经管理员会话和本机管理 socket 按需返回，普通调用密钥没有读取权限。

每把密钥可以在管理台绑定模型白名单：绑定后该密钥只能调用列出的模型，`GET /v1/models` 也只返回这些模型；留空表示不限制。绑定同时保存在密钥库里，重启后继续生效。

绑定按**完整模型名逐字相等**匹配，不做前缀解析、不做任何降级。绑定 `cn:glm-5.2` 只放行请求里的 `cn:glm-5.2`，不放行 `global:glm-5.2`，也不放行裸名 `glm-5.2`；反过来绑定裸名只匹配裸名请求，不会因为裸名归 CN 域就顺带放行 `cn:glm-5.2`。要同时放开两个域就在绑定里各写一条。绑定值应当直接取自 `GET /v1/models` 的完整模型名，管理台的下拉框就是按这个列表给的。

写入侧会拒掉不带 `cn:` / `global:` 前缀的裸名，返回「模型绑定必须填完整模型名」。读取旧文件时不做这个检查：一份历史上存过裸名的密钥库仍然能正常打开、原密钥继续鉴权，管理员把那条绑定改对即可，不会因为升级而让所有密钥一起失效。

每把密钥还可以设置有效期。既有密钥与新建密钥默认都是**无限制**，不会因为升级而被加上到期时间；创建或编辑时可以选择 7 / 30 / 90 天、1 年或自定义时间。到期后该密钥立即失效，网关返回 `api_key_expired` 而不是笼统的「密钥无效」，重新设置有效期即可继续使用。有效期只影响鉴权，不改变密钥的启停、模型白名单或用量记录；密钥列表的「总用量」列显示该密钥累计的 token 数，完整明细见用量统计页。

共享同一密钥文件的进程会串行读改写，并在鉴权时检查文件更新；其他实例停用或删除的密钥不会继续被旧缓存接受。运行时发现文件损坏会拒绝鉴权，保留原文件供修复。密钥文件上限为 8 MiB，用量账本上限为 64 MiB，读写采用相同限制。

## Docker 目录权限

镜像用户是 `10001:10001`。`auths/` 与 `data/` 需要该用户读写，`config.json` 需要该用户可读。

新增账号必须重启加载。容器内运行登录脚本会按镜像用户写文件；若在宿主机导入账号，需要同步检查文件的所有者和 0600 读取权限。

管理台在宿主机使用同一个 `data/` 目录连接 socket。共享目录，避免单独挂载重启时会被替换的 socket 文件。socket 包含管理能力，不能公开反向代理。

## 热更新

热更新让部署者不必重新 `docker compose build`：管理台「系统 → 版本与热更新」点一次「立即更新」，网关从 `update.repo` 的 GitHub Release 下载本机架构的二进制（`wb2api-linux-amd64` / `wb2api-linux-arm64`），校验 Release 提供的 SHA-256 摘要，然后把监听套接字交给新实例。

```json
{
  "update": {
    "enabled": true,
    "repo": "dddmiku/workbuddy2api",
    "token": "",
    "dir": "/app/data/updates"
  }
}
```

关掉热更新的效果是 `GET /update` 与 `POST /update/apply` 返回「未启用」，只能手工重新部署。

机制与前置条件：

1. 容器入口是 `docker-entrypoint.sh`（PID 1）。它以子进程方式运行网关，所以交接后 PID 1 不会跟着消失，容器不重建。
2. 旧进程把监听套接字以继承 FD 传给新进程，新进程报告完整就绪后才提交 `current`，随后旧进程停止接受新连接，并继续处理在途请求（包含流式对话）；收尾等待上限 15 分钟。候选启动或就绪失败会终止候选、保留旧指针和旧服务。
3. 新进程以 `WB2API_LISTEN_FD=3` / `WB2API_READY_FD=4` 启动，读同一个 `config.json` 与 `data/`，因此账号池、密钥库和用量账本继续可用。
4. 下载件与 `current` 指针写在 `update.dir`。容器重启后 PID 1 优先执行 `current` 指向的二进制，所以升级后的版本不会在重启时回退。
5. 使用相同账本字段的进程在文件锁内按「本方增量」合并。跨旧版本时需查看发布边界：旧写入者不能保留自己不认识的新字段，不应将同格式并发验证外推到所有旧版本。
6. 管理通道的 Unix socket 也一并继承：旧进程还在服务同一个路径时，新进程没法重新 `bind`。旧版本（v1.3.1 及更早）不会交出来，新版本会在后台等旧进程收尾释放路径后自行接手，期间管理台可能短暂读不到数据，主服务与在途对话不受影响。
7. PID 1 会向热更新后的服务进程转发停止信号；后继进程意外退出时容器退出，由部署的重启策略处理。服务关闭时先结束 HTTP、定时任务与会话清理，再完成用量、账号池和 Redis 的落盘。

更新目录由入口脚本与 Go 进程采用同一规则解析：`WB2API_UPDATE_DIR` 优先，其次 `update.dir`，再依据 `state_file`（含 `WB2A_STATE_FILE` 覆盖）推导。相对路径以进程工作目录为基准。

共享 `state_file` 的新版进程会在跨进程文件锁内合并本方变更：计数与扣费累加，模型限额逐键合并，显式启停、余额赋值和删除保留各自意图。旧实例最后一次落盘不会用旧快照覆盖整份新状态。该保证要求参与写入的进程都使用新实现；旧二进制不会自动遵守新锁，因此首次升级采用下面的完整镜像重建流程。

**前置条件：运行中的版本必须不早于 v1.3.4。** 更早的版本在交接后会提前结束旧进程（容器被 PID 1 一起带走，正在进行的对话会被截断），也有的会把管理 socket 关掉。这些版本请先按常规方式重新部署新镜像。

**v1.3.16 包含入口脚本、随镜像分发的任务脚本及管理台修复，需要更新网关和管理台完整镜像。** 只下载 Go 二进制不会更新这些组件。重建前备份 Compose、数据和 `current`；将 `current` 切换为已核验的新二进制，或移除该指针以使用新镜像内置版本，并在启动后核对 `/healthz` 版本与实际运行文件的 SHA-256。旧指针仍存在时，仅更换镜像可能继续运行旧版本。

**v1.3.19 同样需要完整镜像更新，并先停止旧进程后启动新版。** 本版增加失败/用量未完整返回的账本计数及面板显示；v1.3.18 或更早进程重写同一个文件时会丢掉不认识的新计数字段。仅热换二进制不能更新面板，也不能保证旧写入者交接期间保留这些字段。正常更新保留原有累计量，不按上下文倍率重新计算历史。

常规容器停止时 HTTP 收尾预算为 5 秒；Compose 的 `stop_grace_period: 3m` 为任务取消和持久化留出额外时间，不表示每条流式请求都能等待 3 分钟。常规重建需要安排短暂维护窗口。

回滚与清理：

```bash
sudo rm -f data/updates/current        # 丢掉指针，回到镜像内置二进制
sudo docker compose restart wb2api
sudo rm -rf data/updates/*-wb2api-linux-*   # 确认不再需要旧下载件后清理
```

容器需要能访问 `api.github.com` 与发布资产地址。断网环境把 `update.enabled` 设为 `false`，改用 Release 附件手工升级。

## 定时任务

每个任务使用 `schedule.<key>_enabled` 开关和 `schedule.<key>_hours` 小时列表，小时按服务时区解释。Compose 默认时区为 `Asia/Shanghai`。

任务包括 `checkin`、`travel`、`activity`、`keepalive`、`school`、`cat`、`redeem`、`lottery`、`makeup`。关闭任务应设置对应开关为 `false`，空小时列表不会表示禁用。

同一实例中的任务执行使用互斥以隔离各自日志，同时到期的任务会排队执行。

手动触发返回已接受后由调度器持有生命周期，不会因为提交操作的 HTTP 连接结束而取消。服务关闭会取消任务，并等待已经接受的工作结束；取消后不再启动下一段上游 RPC。Redis 写队列保序，关闭时等待已接受的写入，超时会明确报错。

活动任务依赖上游接口和开放状态。首次部署可先关闭不需要的任务，再逐项启用。

## 国际版注册地补全

国际版账号如果在官方登录流程里没有确认国家/地区，`chat` 会被上游以 `429` + `code 14017`（`The trial version is not yet activated`）拒绝，并且不会自行恢复。网关在命中该错误时会补交注册地后用同一个账号重试一次；每天 22:00 的 `keepalive` 也会为全部国际版账号补一次，已经登记过的账号只多一次无副作用的激活调用。

补交动作使用出口 IP 探测到的地区，与官方登录页「Complete Your Profile」等价。修复成功的账号不会留下冷却，`14017` 的命中时间仍记录在账号的最近活动里。

## 环境变量

服务支持部分 `WB2A_*` 覆盖项，具体列表以 `cmd/server/config.go` 的 `applyEnv` 为准。`api_keys_file`、`api_keys_socket` 当前通过 JSON 配置，不应假定所有字段都有对应环境变量。

`features.sanitize_blacklist_fingerprints` 仅保留旧配置兼容，已废弃，不再修改请求正文。
