# Trae glm-5.3 首内容延迟：第四阶段报告

日期：2026-11-14（Asia/Shanghai）。基线：main / `6db0ec4` / v3.15.14。
范围：生产日志和状态只读；真实请求通过本地隔离 handler、生产同源 Trae 适配器及 SSH SOCKS 的 VPS 出口执行。凭据只经内存和子进程 stdin 传递，没有写入测试源码、命令参数、日志或报告。未部署、重启、修改线上配置、提交或推送。

## 1. 根因与分段证据

**Confirmed：本轮复现的 GLM 长上下文首正文等待，主要在 Trae 远端生成环节；不在目录查询、网关准备或 SSE 转译。** 同账号、同输入、同 Remote 路径的成功样本中，GLM 在响应头后 27.304s / 38.251s 才出现正文；DeepSeek 为 3.361s / 7.322s。转译约 0–0.505ms，正文准备就绪到客户端收到约 0.101s / 0.378s。不能把保活时间当成真实首内容时间。

**Confirmed：网关还存在两处独立缺陷。** 目录/建会话/等头期间无保活，客户端首字节额外等到上游建流后；首模型事件的滚动窗口在检查前截断，导致大块读取中的合法事件前缀漏判。两处都已用红/绿回归锁定并修复。第二处是否解释首次 126.670s 的真实失败，仍为 **Inferred**，因为原次探针没有保留错误机器码，不能单凭耗时认定。

### 分段定义

- `prepare_ms`：Trae 请求构造，包含本次目录等待；因此 catalog 与 prepare 不相加。
- `create_ms`：Remote 建会话 RPC 及响应解析。
- `header_ms`：收流请求写完到最终响应头返回；连接获取单独观测，连接均复用。
- `first_event_ms`：响应头之后第一个完整 SSE 事件，包括状态/心跳；**不代表模型输出**。
- `first_token_ms`：响应头后转译器首次产生非空 reasoning/content，排除 role 和保活。另记录原始 upstream_reasoning、upstream_content。
- `translate_ms`：首输出事件的转译耗时；`write_ms`：首实际下游 Write 耗时。
- `first_byte_ms`、`first_content_ms`：客户端测量，从请求开始到首保活/首正文，分别报告。

所有实测都记录在工作区 `../artifacts/gateway-stage4-timing/` 的安全 JSON 中，无原始请求正文或模型输出。

### 推理与正文的区别

GLM 修复版在响应头后 5.746s 已出现原始 thought，正文却到 38.251s 才出现；DeepSeek 原始 thought 5.411s、正文 7.322s。当前 Remote/translator 有正文前推理合并策略，避免客户端产生碎片 thinking blocks（`stream.go:1418,1521,1708`）；本轮没有删除该策略或放宽循环保护。因此原始 thought 到达不等于客户端已收到真实正文，也不能据此说正文已被网关扣住三十秒。

**Inferred**：长上下文下 GLM 的推理/Trae agent 执行负载明显贡献等待。现有事件无法进一步精确分离 Trae 内部排队、模型 prefill 与推理计算；不把“远端等待”强行写成某一 GPU 或 tokenizer 根因。

### 其他真实样本与失败

- 简单“只回复 OK”请求：同账号 GLM 首正文 6.944s；重复文本大输入为 9.768s。高信息熵大输入为 14.028s。说明不是所有请求固定 20+s。
- 第一次复杂基线 GLM 在 126.670s 以 stream_error 结束，没有首正文；对照 DeepSeek 正常完成。该次仅保留了安全机器类别，没有原始错误文本，不能当成成功延迟数据，也不能断言它就是大帧漏判造成。原记录为 `before-results.json`。
- 复跑基线 GLM 正常完成但首正文仍为 29.570s。记录 `repeat-results.json`；修复版为 `after-results.json`；简单及冷目录样本为 `before-repeated-results.json`、`before-unique-cold-results.json`。
- 大帧缺陷的**因果证明来自确定性单测**，不是把上述一次失败/成功的差异都归给代码。

## 4. 上游慢时，网关还能做什么

已完成：把目录/建会话/等头期间的连接保活前移，避免客户端一直等不到任何响应；保留真实首正文、首推理、首字节的独立计量；修复活动事件漏判，不因滚动窗口错误误杀已经活动的流。

不应做：用保活伪造内容或 usage；扩大超时掩盖等待；静默替换模型、切 dev 档、降低请求上下文或改变思考选项。

可另行评估：在明确支持的客户端显示“连接中/推理中”的协议进度；评估原始推理流如何展示并兼容连续 thinking block 与循环重试。这里会改变展示/重试契约，不能为了首字指标直接去掉保护。本轮未做这些行为改变。
